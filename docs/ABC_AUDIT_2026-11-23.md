## Resumen
Hay dos experiencias separadas: el juego principal Godot (prototipo de supervivencia/gestión) y una demo web Vite con Phaser/Three.js. La web tiene un loop de combate corto y una base visual provisional, pero no es una exportación de Godot. La prioridad es convertir módulos existentes en un loop comprobable, evitar duplicación de sistemas, corregir publicación y luego elevar la presentación.

## Estados
- **Implementado/prototipo:** hay código y un flujo parcial.
- **Pendiente integración:** módulos escritos sin flujo completo visible.
- **Pendiente validación:** requiere prueba manual o dispositivo.
- **No implementado:** no afirmar que existe.

## Hallazgos de Vercel (evidencia de logs)
- Hay **tres proyectos Vercel** con nombres similares, lo que puede confundir URLs y destinos.
- En el proyecto `titanes-del-pacifico`, la compilación ejecuta `npm run build` y Vite genera `dist/`, pero la configuración de salida de Vercel no encuentra `dist` y termina en `STATIC_BUILD_NO_OUT_DIR`.
- El build sí alcanza `tsc -b && vite build`; Vite reporta advertencia de `@import` de CSS en orden no válido y un chunk JavaScript minificado de aproximadamente 2 MB.
- Dos proyectos con nombres alternativos registran deployments READY, pero READY confirma el build/deployment, no una prueba manual del juego en navegador. La protección SSO está activada para dominios Vercel en los proyectos consultados.
- Se añadió `vercel.json` con framework Vite, comando de build y salida `dist`. Debe verificarse en una nueva build; aún no se declara corregido hasta que el deployment final sea READY y se pruebe la URL.

## P0 — Orden de trabajo inmediato
1. **Web deploy:** confirmar que Vercel usa `vercel.json`, compilar, comprobar salida y abrir URL; resolver SSO si impide acceso público.
2. **Loop web:** misión 1, movimiento, combate, pausa/reinicio, resultado, recompensa única, hangar/unidad y restauración de progreso.
3. **Godot:** importación en Godot con renderer real, cero errores, recorrido de exploración/recolección/base/misión/guardado.
4. **Persistencia:** inventario explícito de campos; test de guardar-cargar por manager; backup y migración.
5. **Conectar managers:** integrar misión, expedición, eventos, región, crafting y supervivencia, sin crear sistemas duplicados.
6. **Controles/UI:** teclado, táctil, mando; safe areas; cámara táctil; pantallas contextuales.
7. **Contenido:** segundo escenario jugable y Kaiju con comportamiento diferenciado antes de ampliar la campaña a 12 misiones.
8. **Arte/audio:** sustituir primitivas gradualmente por assets originales; no esperar a tener todo el arte para probar gameplay.
9. **Online:** permanecer desactivado hasta Auth, RLS, moderación, bloqueos/denuncias, límites y pruebas servidor estén listos.
10. **Release:** exportar Android/Web/desktop y validar cada artefacto en dispositivo real.

## Definition of Done (para cada sistema)
- Flujo accesible desde la escena/UI; no solo script aislado.
- Caso correcto, incorrecto y límite probado.
- Costo/recompensa no se duplica y no cambia con entrada inválida.
- Guardado/restauración cuando corresponda.
- UI informa estado y error.
- Prueba automatizada/CI y prueba manual documentada.
- No marcar plataforma o feature como terminada por configuración/preset.
